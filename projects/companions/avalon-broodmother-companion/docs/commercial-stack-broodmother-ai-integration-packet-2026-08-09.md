## Verdict

Proceed with this packet as the complete proposed integration contract. Do not implement from it until an independent review record and named human promotion owner make its material claims current authority.

The requested architecture is compatible with the permanent provider boundary: Rabbit remembers, GOAP reasons, PlayMaker choreographs, Blaze performs physical behavior for `BlazeOwned` actors, and Avalon Runtime V2 owns admission, leases, cancellation, and cleanup. The current Brood Mother implementation does not use that path: the live plugin calls `BroodmotherCompanionAiV1Contract.Evaluate(...)`, links only the primitive evaluator source, declares two generic roles, declares no Rabbit keys, and declares no PlayMaker requirements. The current Blaze provider implements only the stay-idle proof, while the current PlayMaker provider implements only `avalon.core.use-interactable.v1`. All Spider-specific executor, command, procedure, interrupt, and ownership capabilities below are required new work, not existing capability claims.

The target route must fail closed. There is no fallback from the commercial stack to the current static evaluator.

## Rabbit Blackboard Pro schema

### Ownership model

Rabbit remains memory, not game truth and not a second save system.

- The FoA/Avalon host writes authoritative actor observations.
- `BroodmotherPackCoordinatorV2` alone computes pack reservations from the current set of valid leased actors, then replicates the result into each actor's authoritative Rabbit observation batch.
- Rabbit-derived signals convert authoritative values into planner-friendly booleans/bands.
- Goal policies remain read-only. A host/runtime integration component named `BroodmotherPackageMemoryCommitterV2` obtains the exact actor/manifest-bound `IAvalonPackageBlackboard` and writes only the declared package-local keys after role binding, goal selection, procedure stage changes, and terminal action results. It never writes during `IAvalonGoalPolicy.Evaluate(...)`.
- No package key uses `BlackboardScope.World`. Cross-actor coordination is owner-computed because the current Rabbit actor backend does not implement a world context.
- No key is persistent. Actor release, package revoke, runtime stop, scene loss, companion dismissal, and invalid Unity ownership all discard the context.

### Pack-coordination rules

1. The coordinator considers only actors with an exact active Runtime V2 lease and matching `pack.id`.
2. There is one global damage-commit slot. Flank, reposition, retreat, and recovery may run without it; bite, leap contact, and spit launch require it.
3. Requests are ordered deterministically by emergency first, then finisher-on-weak-target, then starvation age, then stable role order, then `ActorId` ordinal. No random or `PackIndex` role reassignment is permitted.
4. The reservation is identified by actor ID, action kind, target ID, and generation. Every procedure re-tests all four before opening a damage window.
5. A reservation expires on lease change, target change, procedure terminal outcome, timeout, interruption, actor release, or cleanup request.
6. Flank sides alternate across currently valid flankers using stable role order and actor ID; the assignment changes positioning only, never role identity.
7. The finisher claim is exclusive per target and exists only while `target_weak` remains true.
8. Coordinator failure writes no grant, requests interruption of any uncommitted procedure, and blocks new damage actions. It never falls back to the static evaluator.

`BroodmotherRoleActionCostProvider` evaluates from the immutable planning snapshot:

- add `8.0` when an attack action lacks its exact slot (the action should normally be precondition-ineligible; the cost is defense in depth);
- add `3.0` when the current distance band is one band from the action's preferred band;
- add `6.0` when it is two or more bands away;
- add `4.0` for a front-lane leap;
- add `5.0` for spit when the ranged lane is not clear;
- add the role-specific finisher penalty above;
- return a finite non-negative value or fail the plan as invalid.

### Replanning and interruption rules

Current Runtime V2 marks a context dirty after new observations but does not use `AvalonActionDefinition.InterruptPolicy` to cancel a running action. Commercial-stack implementation therefore requires an explicit, separately reviewed Runtime V2 interrupt evaluator after observation commit.

| Trigger | Runtime response | Procedure response |
|---|---|---|
| lease/generation mismatch, cleanup, runtime stop, actor release | immediate cancel regardless of commitment | run idempotent interruption cleanup and return `Interrupted` |
| target invalid or target ID changed | apply `OnInvalidTarget` | close damage window; cancel command; release reservation |
| damage revision increases | apply `OnDamage` to flank, reposition, leap wind-up, spit wind-up, and recovery | retreat/recover becomes eligible; an airborne leap disables damage and executes safe landing/abort rather than transform teleport |
| threat closes into unsafe band | apply `OnThreatIncrease` to spit, flank, and reposition | cancel uncommitted command and replan retreat/reposition |
| emergency goal outranks active goal after minimum commitment | apply `OnGoalChange` | terminate at the next safe procedure boundary |
| procedure timeout, poll fault, command fault | cancel action and current plan | return a normalized retryable/terminal result, then require recovery or stop |
| ordinary new observation with no trigger | keep active action | update memory only; do not thrash the plan |

Replanning is bounded by Runtime V2 `MinimumReplanInterval`, package `MaximumPolicyCadence`, goal commitment, and a maximum of one plan replacement per actor per observation revision. The exact interrupt evaluator and tests are a foundational Runtime V2 change and require their own source gate before implementation.

## PlayMaker 2 procedure contract

Every procedure is private, versioned `v1`, mutates only through Avalon actions/commands, runs inside one `AvalonActionExecutionLease`, and exposes the standard terminal events `AVALON_SUCCEEDED`, `AVALON_FAILED_RETRYABLE`, `AVALON_FAILED_TERMINAL`, `AVALON_INTERRUPTED`, `AVALON_REJECTED`, and `AVALON_TIMED_OUT`.

Common required inputs are execution ID, invocation ID, exact actor lease/generation, role ID, target descriptor, observation revision, reservation generation, deadline, and granted capabilities. Common outputs are outcome, failure code/message, final stage, consumed reservation generation, produced facts, command statuses, and diagnostic tags.

| Procedure ID | Timeout | Required FSM sequence |
|---|---:|---|
| `avalon.broodmother.spider.procedure.bite.v1` | `1800 ms` | validate lease/capability/target/slot -> face target -> bite telegraph -> play bite clip -> open guarded bite window once -> close window -> release slot -> terminal |
| `avalon.broodmother.spider.procedure.leap.v1` | `3500 ms` | validate side/rear angle and slot -> face launch vector -> leap telegraph -> start custom leap clip and Blaze leap arc -> poll launch/contact/landing -> open contact window at most once -> close -> safe landing -> release slot -> terminal |
| `avalon.broodmother.spider.procedure.spit.v1` | `3000 ms` | validate ranged lane and slot -> face target -> gilded telegraph -> start approved high-quality spit VFX -> launch guarded spit command once -> poll result -> stop/recycle VFX -> release slot -> terminal |
| `avalon.broodmother.spider.procedure.flank.v1` | `2500 ms` | validate lease/target/flank side -> request owner-resolved flank position -> Blaze move/facing command -> poll arrival -> terminal; no damage window |
| `avalon.broodmother.spider.procedure.reposition.v1` | `2200 ms` | validate role band -> request owner-resolved role position -> Blaze move/facing command -> poll arrival -> terminal; no damage window |
| `avalon.broodmother.spider.procedure.retreat.v1` | `2500 ms` | close any window -> release attack slot -> request owner-resolved safe position -> Blaze retreat command -> poll arrival or safe stop -> terminal |
| `avalon.broodmother.spider.procedure.recovery.v1` | `1400 ms` | stop attack motion -> play role recovery clip/state -> verify lease and grounded/control-ready result -> clear recovery-required -> terminal |
| `avalon.broodmother.spider.procedure.interruption.v1` | `500 ms` | mark cancellation -> close damage window -> cancel active Blaze/host commands -> stop/recycle VFX -> release reservations -> clear procedure-local state -> return `Interrupted`; all steps idempotent |

Spider-specific PlayMaker whitelist additions must be custom Avalon actions such as `Avalon.RequestSpiderFace`, `Avalon.RequestSpiderMove`, `Avalon.RequestSpiderAnimation`, `Avalon.RequestSpiderLeap`, `Avalon.RequestSpiderDamageWindow`, `Avalon.RequestSpiderSpit`, `Avalon.ReleaseSpiderReservation`, `Avalon.StopSpiderVfx`, and `Avalon.InterruptSpider`. Direct `Transform`, `NavMesh`, physics, animation, health, damage, object creation/destruction, save, reflection, FoA, or Blaze actions remain forbidden in templates.

Leap integration is complete only when GOAP selects the leap action, Runtime grants the exact lease/capabilities, PlayMaker runs the leap procedure, Blaze executes the custom motion/animation, the guarded host opens at most one contact window, and landing/recovery feeds a terminal result back into Rabbit/GOAP. Playing the clip or spawning an arc VFX by itself is not an implemented leap attack.
