## Approach

- Patch type or plugin behavior: `BaseUnityPlugin` load/config scaffold with Harmony patches limited to companion UI input locking. A lightweight `Update` gate waits for common references, `Hero.Current`, and loaded templates, then logs pet/summon diagnostics, writes a template taxonomy CSV, writes scene-spawner-backed pet/creature candidate CSVs once when explicitly enabled, optionally crosschecks those candidates against the latest FOA-Diagnostic Tool `spawner_refs.csv`, can write default-off actor-control proof CSVs plus dry-run command logs, can run one optional Avalon Core trust-report reflection diagnostic, can run one default-off AI boundary diagnostic for active managed companions, can run one default-off AI profile/intent audit classifier for active managed companions, and can run one gated profile-driven native assist loop. A pet companion controller handles roster selection, summon/swap, recall, dismiss, recover, follow/stay hotkeys, explicit Follow/Stay/Defend modes, throttled native defend prompting while the hero has live attackers, Come Close/Heel, Close/Normal/Far follow range commands, metadata/status-only continuity, responsive refresh scheduling for existing follow/defend ticks after explicit commands, runtime trust/loyalty scoring, bond-policy timing modifiers, profile-only progression storage, command audit logging, lifecycle checkpoint logging, per-active-companion status display, a styled plugin-owned IMGUI debug panel that can optionally render selected companion icons from Tainted Interface and exposes visible `AI Boundary Check`, `AI Profile Check`, `Progression Gate`, `Taming Gate`, and `Encounter Probe` smoke buttons, a plugin-owned vanilla-style Unity UI custom dialogue host, optional Tainted Interface/FoA Mod Manager input-scope acquisition, runtime attachment/removal of one `AvalonCompanionCommandAction : AbstractLocationAction` `Companion` prompt by default, and fallback runtime attachment/removal of native quick-command action elements only when `Companions.EnableNativeCommandMenu=false`. Version 0.1.40 changes companion behavior only behind `Companions.EnableProfileDrivenNativeAssist=true`, routes `FollowCatchUpCandidate` to existing catch-up recall and `NativeCombatObserved` to existing native ally defend prompting, and makes the matching legacy follow/defend ticks stand down while the profile gate is enabled. Version 0.1.42 changes no runtime lifecycle behavior; it documents the throwaway-save lifecycle validation route. Version 0.2.10 saves only approved profile fields to `companion-profiles.tsv` and loads only trust/loyalty profile values. Version 0.2.11 writes only one read-only `taming-eligibility-gate` row from reviewed roster identity and runtime role/temperament classification. Version 0.2.12 writes only read-only `companion-taming-encounter.csv` rows for nearby reviewed wolf/bear live actors. It does not add native story dialogue, custom target selection, movement-state overrides, target override elements, attack UI, capture/taming commands, training, actor persistence, reload restoration, auto-respawn, re-adoption, an Avalon Core reference, BepInEx dependency, adapter descriptor registration, companion-profile registration, Core registry query, or Core runtime callback.

- Save impact: diagnostics only read live world/template/spawner state, optionally read the latest FOA-Diagnostic Tool CSV dump under BepInEx config, optionally read Avalon Core's copied host trust-report snapshot by reflection, log one line, and optionally write plugin-owned config CSVs. Actor-control proof diagnostics only classify live locations/components and write dry-run command decisions; they do not move, target, spawn, persist, or command actors. The AI boundary diagnostic appends `companion-ai-boundary.csv` only under this plugin's config folder and records unchecked native state for active managed companions while explicitly reporting `touchesCommands=false`, `touchesMovement=false`, `touchesTargeting=false`, `touchesPersistence=false`, and `coreExecuted=false`; it avoids native target recalculation and `TargetOverrideElement.GetTarget`. The AI profile audit appends `companion-ai-profile.csv` only under this plugin's config folder and classifies observed active managed companion state into runtime-only `CompanionAiProfile` / `CompanionAiIntent` rows while explicitly reporting the same false mutation/Core flags. The profile progression store appends/rewrites `companion-profiles.tsv` only under this plugin's config folder, keyed by template GUID plus review ID, and stores only approved identity/trust/loyalty/bond profile fields; loading hydrates trust/loyalty profile values only and does not restore actors or apply stored mode/range to command behavior. The taming eligibility gate appends only one `taming-eligibility-gate` row to `companion-command-log.csv` from reviewed roster identity and existing role/temperament classification; it does not read nearby wild actors as adoption targets, save actor data, or modify any live actor. The taming encounter probe appends `companion-taming-encounter.csv` rows for nearby reviewed wolf/bear live actors and records native state without capture, wild actor adoption, faction changes, ally attachment, target recalculation, movement changes, actor persistence, or command behavior changes. The Avalon Core diagnostic bridge does not write files, register descriptors, register profiles, query mutable Core services, or change gameplay. Pet companions are marked not saved and managed if they match the validated runtime-approved Qrko roster GUIDs plus the not-saved marker. Animal/creature one-session candidates are spawned only by explicit player command, must expose an `NpcElement`, are marked not saved, receive the native summon-faction plus `NpcHeroPetAlly` marker, and are tracked only in memory for the current session. If the ally marker cannot be applied, the spawn is discarded. Their native companion command action is also marked `IsNotSaved`, is attached only while the live actor remains in the runtime candidate registry, and is removed before dismiss/shutdown. Avalon controls for them remain limited to rear-quarter placement, recall/catch-up, managed recovery, dismiss, Heel, Close/Normal/Far range placement, explicit Follow/Stay/Defend modes, and throttled native defend prompts while the hero has live attackers. Defend mode and the automatic native defend fallback call `NpcHeroPetAlly.EnterCombat()` only when the hero already has live attackers; 0.1.10 adds per-companion cooldowns and clears them when attackers clear. 0.1.15 responsive refresh resets only the next follow/defend tick timestamps after explicit commands; it does not clear per-companion defend prompt cooldowns or create new command state. The lifecycle guard periodically re-marks managed actors not saved, detects scene changes and long hero moves, resolves live `NpcHeroPetAlly` parents, discards untracked one-session roster allies, discards excess active roster actors, and appends `companion-lifecycle.csv`. The recovery command runs the lifecycle guard, discards dead or structurally invalid managed actors only when the lifecycle guard is enabled, and recalls live out-of-range managed actors through existing verified placement. 0.1.14 continuity writes only plugin-owned metadata under the BepInEx config file: remembered companion GUID/name, command mode, and follow range. Command logging appends `companion-command-log.csv` only under this plugin's config folder and records command decisions as audit evidence. Existing config may remember low-risk UI preferences and continuity metadata, and the profile store may remember approved trust/loyalty/bond profile fields, but no actor persistence, reload respawn, companion restoration, same-session re-adoption after reload, resurrection, active squads, or save-owned companion path is enabled.
- Compatibility considerations: 0.1.22 should not affect gameplay while companion UI is hidden except for lifecycle checks when the roster is enabled and runtime gates are open. It registers input-lock patches that return immediately unless the companion debug panel or custom dialogue is visible. Future behavior may overlap with summon, world population, respawn, combat, stealth, and quest-state mods.
- Failure behavior: missing references fail at build through MSBuild reference validation. Runtime load should only log plugin status.
- UI route: supported plugin-owned vanilla-style Unity UI custom dialogue host plus separate plugin-owned IMGUI debug panel, chosen because true native FoA dialogue choices require game-authored or safely registered story bookmark/graph data that is not proven for runtime plugin content. The runtime-only native companion action provides a game-owned world prompt entry point labelled `Companion` for managed one-session creature candidates and opens the Unity UI dialogue host. The dialogue surface is gated behind `Companions.EnableNativeCommandMenu` and `Companions.EnableCustomDialogueInterface`, exposes all approved command choices at once as right-side choices, shows context in a bottom dialogue text band, captures the cursor while open, has clearer hover, selected, disabled, and danger row states in 0.1.30, records command-surface audit rows, and closes with `Esc`, `Goodbye`, or after a command choice. The debug panel remains gated behind `Debug.EnableDebugPanel` and `Companions.TogglePanelShortcut`, exposes roster/debug commands and diagnostics, shows current Follow/Stay/Defend mode plus per-active-companion status feedback, optionally displays the selected companion icon from Tainted Interface, and closes with `Esc`, the close button, or the toggle hotkey. Version 0.1.41 formally keeps this Unity UI route as the supported companion dialogue surface. Version 0.1.29 adds a passive, non-interactive gameplay HUD badge for the active managed companion only; it uses cached Tainted Interface textures and hides while the debug panel or dialogue is visible. Directly converting vanilla pet or dialogue menus remains blocked until story graph/bookmark registration and `PetVariantBase` applicability are proven.
- Companion UI input lock route: mirrors the repo FoA Mod Manager fix pattern but splits IMGUI debug-panel handling from Unity UI dialogue handling. While either companion UI is visible, Avalon Companions captures/restores cursor state, forces `CursorLockMode.None` and `Cursor.visible=true`, freezes FoA `GameUI.UpdateMousePosition()`, zeroes `PlayerInput` movement/look fields, and first asks Tainted Interface/FoA Mod Manager for shared custom UI scope when installed. The IMGUI debug panel still disables discovered Unity `BaseInputModule` instances, resets Unity input axes, and neutralizes Rewired axis/button reads while open. The Unity UI dialogue host keeps event modules available and lets Rewired axis/button reads pass so `Button` clicks work through FoA's EventSystem path. The lock only applies while companion UI is visible.

## Future milestone gate

The next behavior milestone must start with a companion target research note. It should identify exact game types and methods for one safe path:

- summon-style temporary ally,
- reused non-unique follower actor,
- non-combat pet or ambient companion,
- dialogue or recruitment-only prototype with no spawned actor.
- dialogue-only command surface that avoids a free-floating gameplay panel.
- runtime-only `Companion` prompt opening a proper command menu without save-owned vanilla interaction edits.

The current research points to this safer behavior order after diagnostics:

- keep the current IMGUI panel as a debug/control surface only,
- validate the 0.1.23 vanilla-style Unity UI custom dialogue host before calling it release-ready,
- research true native story dialogue separately before any `VDialogue`/`StoryBookmark` implementation,
- research custom AI logic only after the command surface is proven and `companion-ai-boundary.csv` plus `companion-ai-profile.csv` evidence is reviewed across peaceful, combat, stealth, interior, transition, rest, quit/reload, and return cases,
- add capture/taming commands, training, behavior-changing loyalty, and other progression features only after command surface, actor ownership, persistence boundaries, and custom AI hooks are approved,
- keep explicit player-commanded re-summon on the existing one-session path as the only continuity actor path,
- keep actor restoration, saved ownership, auto-respawn, and same-session re-adoption after reload blocked until a full rest/quit/reload validation pass exists,
- load a throwaway save with diagnostics enabled,
- confirm whether a native pet already exists,
- confirm loaded `Spec_Pet_*` template GUIDs and common pet references,
- write and review the pet/creature scene-spawner-backed candidate shortlist before adding any non-Qrko pet or creature to the roster,
- exercise the Avalon pet/animal companion roster,
- do not implement humanoid companions until exact actor, faction, quest, and persistence behavior is researched.
